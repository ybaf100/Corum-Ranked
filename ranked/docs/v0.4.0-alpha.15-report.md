# Corum Ranked v0.4.0-alpha.15

## Scope

This patch rebuilds attempt accounting around one invariant: every visual Geometry Dash attempt observed by the Ranked client must produce one ordered server start/end pair, even when gameplay resets faster than the network can acknowledge the previous pair.

## Attempt transport / lost-score fix

The old client had one `pendingEnd` slot and one deferred next-start slot. A fast sequence could therefore become:

1. Attempt 1 ends and `/attempt/end` is still in flight.
2. Geometry Dash immediately starts Attempt 2.
3. Attempt 2 ends before Attempt 1's HTTP acknowledgement returns.
4. The single pending-end slot is still occupied, so Attempt 2's end could be discarded.

alpha.15 replaces that model with a FIFO visual-attempt backlog. Each queued item owns its start event and optional end event. The transport serializes those items against the authoritative server without overwriting a later attempt. Pre-ack deaths/Clears remain attached to the correct start and are sent immediately after that start is accepted.

Manual restart/reset is also treated as an attempt end when `destroyPlayer()` did not already close the attempt. Manual quit follows the same exactly-once rule.

## Score / Clear synchronization

- Ranked scores are represented as `double` in the client. Decimal Qualifying values are preserved; e.g. Qualifying `20.1` gives a Clear score of `120.1`.
- `/attempt/progress` returns a live `displayScores` snapshot after Qualifying.
- `/attempt/end` returns authoritative committed `scores` and `clears` immediately.
- Ended-but-unacknowledged attempts contribute an optimistic score/Clear overlay. Each contribution is removed individually when its own authoritative acknowledgement arrives, so multiple fast attempts can be displayed without dropping or double-counting one another.
- A current visual attempt's live progress is added on top of already-ended optimistic attempts. Once the current attempt ends, its live value is suppressed because its final value has moved into the optimistic backlog.

## Two-Clear / LAST ATTEMPT race

A pending second Clear blocks LevelInfoLayer from creating another visual attempt until the server acknowledges that Clear and returns the resulting phase. Attempt-end snapshots carry the phase and LAST ATTEMPT metadata, so spectator/target state is applied immediately rather than waiting for the next match poll.

The 10-second LAST ATTEMPT value remains a start window only. An attempt accepted inside that window remains valid through completion in `ROUND_SETTLING`.

## Death Match

- Server-side start remains authoritative and rejects attempt 4+ with `DEATHMATCH_ATTEMPTS_EXHAUSTED`.
- The client reserves a local visual attempt before PlayLayer begins, preventing network acknowledgement latency from rendering a fourth attempt.
- `attemptsUsed`, `attemptsCompleted`, live scores, and live progress are included in Death Match snapshots.
- Fast resets are serialized by the same FIFO attempt transport used by normal rounds.
- After the third visual attempt, no new LevelInfo -> PlayLayer entry is allowed. The client waits for the opponent/result.

## Countdown UI

- Gameplay countdown is centered at the screen midpoint and enlarged to scale `0.66`; the state text below it uses `0.40`.
- Match-found and round-preparation countdowns are also center-anchored and enlarged.

## Compatibility

No Apps Script schema or PostgreSQL migration is required. Corum Integration is unchanged.
