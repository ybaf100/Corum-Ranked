## Evidence and changes

### Native entry without 3/2/1 or gameplay

The supplied beta.83 iPadOS log (`Geode 2026-10-18 20.45.21.log`) downloads Colorado, GD 91780215, including 657,048 geometry bytes and audio. At 20:45:57 the client reaches ROUND_ENTERING and completes native setup/hold. Native scene entry is logged only at 20:46:05, after Pause manipulation. Railway HTTP logs show both iOS and Android64 ready requests accepted, subsequent state requests and session heartbeats accepted, and no `/entered` at launch. iOS finally submits `/entered` at 11:46:05.129 UTC (201). This distinguishes an entry progression gap from a failed resource download, rejected API or suspended server.

The beta.83 fallback has two source-level defects reproduced by executable tests: it explicitly excludes `survivalLevel`, and rejects a held child with `isRunning()==false`. The entry methods themselves also require that flag before submitting ENTERED. In addition, init sets GD's native pause flag before normal scene entry; native lifecycle/scheduler progress then becomes a prerequisite for the handshake intended to release that hold. The device log does not expose the internal GD scheduler or identify which native writer changes its running flag; that native mechanism remains a device verification item.

`PlayLayer.cpp` now leaves the native pause flag unchanged during init. Existing GJBaseGameLayer update, postUpdate, input, audio and evidence gates hold gameplay; they already prevent physics/attempt publication before GO. An initial WAIT overlay is populated immediately. The process heartbeat serves both Solo and Survival held entries. ENTERED requires the exact current PlayLayer attached to the active scene with no pending transition, independently of scene-local callbacks. GO additionally requires a running native owner/parent, exact match/round/map, authoritative server entered state and startsAt, valid gameplay authority, and the existing native completion/refusal checks. Ordinary GD and spectators do not acquire this hold. Existing Placement rules/protocol are unchanged.

This repairs the actual missing handshake path rather than inventing a three-second local start. The five-second ready-room delay and the three-second shared server countdown remain unchanged. Logs now include the first three process entry pulses (`level`, `survival`, `running`, `paused`) and an explicit Survival GO, in addition to ENTERED and ACK logs.

## Adaptive NORMAL attempts

The old `survivalBotPlan` generated a fixed Gaussian record and jumped to it; Death Match produced three final attempt scores immediately. It has been replaced by the shared pure `survival-bot-simulation.ts` and trusted batch frame application in `survival-match.ts`. Debug and online drivers use the same implementation.

- Fifteen bots use 3 strong, 8 peer and 4 weak personalities. Counts scale with remaining participants. Seeded stable personalities and independent attempt draws vary pacing, mistakes, retry delays and record improvement.
- LP/map prior uses actual Debug human LP (not synthetic matchmaking LP), verified difficulty/demon/length category and up to two recent rounds. Human BEST/time observations use a 16-second EMA; approximately 55% of estimated skill change affects the target skill. Death does not lower BEST or instantly change difficulty. Online uses the upper-half human median and an LP-prior lower bound, so a single deliberate zero cannot lower the group.
- Each attempt begins at zero, advances by fractional progress at a map-length-based speed with mild segment variation, and can die at seeded survival checks or its bounded ceiling. Death resets NOW to zero, retains BEST, and schedules a staggered retry. PB improvement is probabilistic. Adaptation affects future attempts and bounded future-segment hazards, never teleports an active bot or lowers an accepted record. Rare clears are limited to strong bots.
- Death Match uses at most three real-time attempts, retaining three-decimal authoritative scoring, tie/repeat rules and settlement. Human scores, LP/MMR, round cutoff and tied qualification policy are untouched.
- Server simulation uses fixed 500 ms steps and coalesces progress frames. Only BOT participants in the exact round/map context accept these internal frames; there is no public HTTP shortcut around human evidence validation.
- The existing driver_state JSONB stores the seed-derived attempt state, cursor, EMA and progress with the authoritative snapshot in one match transaction. No schema migration is required. Old numeric cursors upgrade from accepted attempts/BEST without replay. Equal/stale simulation times produce no frames. Catch-up is bounded by the round deadline and deterministically replays elapsed steps, not new randomness.
- Database projection reads the match once under its existing lock and batches changed rows/attempts using jsonb_to_recordset. Unchanged round metadata is not rewritten. Old active attempts close before replacement inserts to preserve the partial unique index. A failing batch rolls back snapshot, driver and projections together.
- `SurvivalProgressTween` interpolates confirmed fractional NOW/BEST in the board; the HUD uses confirmed BEST. Attempt IDs reset NOW on death/retry. Older revisions are ignored. No extrapolation creates a server-unconfirmed record; ranks/cutoff/settlement use authoritative values.

Exact level duration is not present in the current map certificate: pacing uses verified GD length categories, not geometry-derived exact runtime. This is an explicit simulation approximation.
